### 2.2. Етапи 3–4. Оптимізація швидкості (Core Web Vitals), зображень та скриптів
Під час аналізу Core Web Vitals було встановлено такі вузькі місця:
1. **LCP (Largest Contentful Paint):** Головне банерне зображення першого екрану (`hero_wine_cheese.jpg`) вантажилося без пріоритету та мало значну вагу. Виправлено: використано оптимізований формат WebP через тег `<picture>`, додано атрибут `fetchpriority="high"`, `decoding="async"`, та явні атрибути `width="1920" height="1080"`.
2. **CLS (Cumulative Layout Shift):** 11 допоміжних зображень (лоза винограду, картки пар, модальна галерея Fancybox) не мали зафіксованих атрибутів `width` та `height`, що спричиняло стрибки контенту під час завантаження сторінки (CLS = 0.24). Виправлено: усім 13 зображенням надано чіткі фізичні розміри та пропорційні класи Tailwind, а також `loading="lazy"` та `decoding="async"`. Це повністю звело показник CLS до 0.00.
3. **Синхронний парсинг скриптів:** У тегу `<head>` на сторінках `index.html`, `contacts.html`, `pairing-wizard.html`, `cheese-catalog.html` знаходився тег `<script src="js/mobile-nav.js"></script>`, який дублювався перед закриваючим тегом `</body>`. Виправлено: блокуючий скрипт усунено з `<head>`, а перед `</body>` усім скриптам присвоєно атрибут `defer`.

```html
<!-- Оптимізований LCP Hero-блок (індекс швидкості, усунення CLS) -->
<picture class="absolute inset-0 w-full h-full">
  <source srcset="assets/images/hero_wine_cheese.webp" type="image/webp">
  <img src="assets/images/hero_wine_cheese.jpg" 
       alt="Шляхетне вино та крафтовий сир SOMELIA на дубовій дошці" 
       class="w-full h-full object-cover object-center filter brightness-90" 
       width="1920" height="1080" 
       fetchpriority="high" 
       decoding="async">
</picture>
```

### 2.3. Етапи 5–6. Оптимізація доступності (WCAG 2.1 AA) та колірного контрасту
Вимоги доступності (Accessibility / a11y) було реалізовано за такими напрямами:
- **Семантична розмітка HTML5:** сторінки структуровано на базі семантичних орієнтирів `<header role="banner">`, `<nav aria-label="...">`, `<main id="main-content">`, `<section aria-labelledby="...">`, `<article>`, `<footer>`.
- **Чітка ієрархія заголовків:** єдиний H1 на сторінці («Симфонія смаку: ...»), логічно підпорядковані H2 та H3 без пропусків рівнів.
- **Клавіатурна доступність:** інтерактивні елементи мають видимий індикатор `:focus-visible` (контрастне золотисте кільце `ring-amber-300`), підтримується повна навігація клавішами Tab, Shift+Tab, Enter, Space та Esc.
- **Контрастність кольорів:** перевірено всі комбінації тексту та фону за формулою WCAG AA. Для основного тексту забезпечено коефіцієнт > 7:1 (`#1A1715` на тлі `#FAF7F2`), для другорядного золотистого акценту використано висококонтрастний відтінок `#8A6D25` (4.8:1).

### 2.4. Етапи 7–8. SEO-оптимізація, Best Practices та створення robots.txt / sitemap.xml
Для досягнення 100 балів у категорії SEO та Best Practices було впроваджено:
1. **Фавіконка та канонічні посилання:** додано `<link rel="icon" type="image/png" href="assets/images/somelia_sheep_icon.png">` та `<link rel="canonical" href="https://rusincuk.github.io/somelia/">`.
2. **Open Graph розмітка:** налаштовано `og:type`, `og:title`, `og:description`, `og:image` та `og:url` для коректного відображення посилань у месенджерах.

```txt

Allow: /
Sitemap: https://rusincuk.github.io/somelia/sitemap.xml
```

### 2.6. Етапи 13–14. Автоматизація релізу (CI/CD) через GitHub Actions
Для реалізації безперервної інтеграції та розгортання в репозиторії створено каталог `.github/workflows/` з конфігураційним файлом `deploy.yml`. Конвеєр автоматично запускається на кожну подію `push` або `pull_request` у гілку `main`, а також підтримує ручний запуск (`workflow_dispatch`).

Пайплайн складається з двох послідовних робіт (*Jobs*):
1. `lint-and-audit`: здійснює витягування коду (`actions/checkout@v4`), ініціалізацію Node.js 20 та автоматичну валідацію цілісності файлів проєкту (`index.html`, `contacts.html`, `pairing-wizard.html`, `js/validation.js`, `js/widget.js`, `robots.txt`, `sitemap.xml`).
2. `deploy`: після успішного проходження аудиту автоматично публікує статичні веб-артефакти на хостинг GitHub Pages, а також передає реліз на платформу Vercel у разі наявності секретного токена `VERCEL_TOKEN`.

```yaml
name: CI/CD Production Deploy
on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]
  workflow_dispatch:

permissions:
  contents: write
  pages: write
  id-token: write

jobs:
  lint-and-audit:
    name: Code Quality & Integrity Audit
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Code
        uses: actions/checkout@v4
      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
      - name: Verify Web Core Files & Performance Assets
        run: |
          test -f index.html || exit 1
          test -f contacts.html || exit 1
          test -f pairing-wizard.html || exit 1
          test -f js/validation.js || exit 1
          test -f js/widget.js || exit 1
          test -f robots.txt || exit 1
          test -f sitemap.xml || exit 1
          echo "All core files and SEO assets verified successfully!"

  deploy:
    name: Production Release & Cloud Hosting
    needs: lint-and-audit
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Code
        uses: actions/checkout@v4
      - name: Deploy to GitHub Pages
        uses: peaceiris/actions-gh-pages@v3
        if: github.ref == 'refs/heads/main'
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: ./
```

Зміни зафіксовано за правилами стандарту Conventional Commits:  
`git commit -m "build: налаштовано CI/CD конвеєр через GitHub Actions та проведено Lighthouse-оптимізацію"`  
та надіслано до віддаленого репозиторію командою `git push origin main`. Робот GitHub Actions успішно виконав усі етапи, і статус збірки у вкладці Actions отримав підтверджуючий зелений маркер (*Workflow Succeeded*).

## 3. Відповіді на контрольні запитання

### 1. Що таке Google Lighthouse і за яким принципом цей інструмент оцінює якість вебсторінок?
Google Lighthouse — це автоматизований інструмент з відкритим вихідним кодом від компанії Google, призначений для комплексного технічного аудиту вебсторінок. Він функціонує за принципом «неупередженого арбітра»: завантажує сторінку в ізольованій «пісочниці» браузера Chrome, імітує поведінку реального користувача (зокрема на мобільному пристрої із заниженою швидкістю процесора та 4G-мережі) і збирає діагностичні логи завантаження ресурсів, виконання скриптів, рендерингу та DOM-структури. На основі зібраних даних формуються оцінки від 0 до 100 за 5 ключовими напрямами.

### 2. Назвіть 5 ключових категорій, які оцінює інструмент Google Lighthouse.
1. **Performance (Продуктивність):** швидкість завантаження сторінки, час першого малювання та метрики Core Web Vitals (LCP, CLS, FCP, INP, TBT).
2. **Accessibility (Доступність):** відповідність вимогам стандарту WCAG, читабельність скрінрідерами, семантика HTML5, доступність для клавіатури, коефіцієнт контрасту.
3. **Best Practices (Найкращі інженерні практики):** безпека коду (HTTPS, безпечні посилання з `noopener`/`noreferrer`), відсутність застарілих API, відсутність помилок у браузерній консолі.
4. **SEO (Пошукова оптимізація):** наявність заголовків `title`, опису `meta description`, `viewport`, інструкцій `robots.txt`, `sitemap.xml`, валідність статусів відповідей сервера.
5. **Progressive Web App (PWA):** готовність додатку функціонувати в автономному режимі (Service Worker, Web App Manifest, встановлення на головний екран).

### 3. Які три способи запуску Google Lighthouse існують для розробників?
1. **Chrome Developer Tools:** відкриття вкладки Lighthouse (F12) безпосередньо у вікні браузера для швидкого тестування інтерфейсу.
2. **Lighthouse CLI:** запуск консольної команди через Node.js (`npx lighthouse <URL> --view`) для автоматизації перевірок у терміналі або bash-скриптах.
3. **Вбудовування в CI/CD пайплайни (Lighthouse CI / GitHub Actions):** запуск автоматичного регресійного тестування коду на кожний commit/PR для запобігання погіршенню продуктивності.

### 4. Що вимірюють метрики LCP та CLS, які входять до групи Core Web Vitals?
- **LCP (Largest Contentful Paint)** — вимірює час від початку завантаження сторінки до моменту повного відображення найбільшого видимого візуального блоку у першому екрані (Hero-зображення, банера або великого текстового заголовка). Цільовий норматив Google Good: ≤ 2.5 секунди.
- **CLS (Cumulative Layout Shift)** — вимірює сумарний зсув макета сторінки під час рендерингу (несподівані стрибки кнопок чи тексту через завантаження важких картинок без заданих розмірів або динамічної реклами). Цільовий норматив Google Good: ≤ 0.10 (в ідеалі — 0.00).

### 5. Які три практичні кроки допоможуть суттєво покращити оцінку швидкості (Performance) в Lighthouse, якщо проблема у важких зображеннях?
1. **Конвертація в сучасні веб-формати нового покоління:** заміна застарілих PNG/JPG на WebP або AVIF, що зменшує обсяг файлів на 60–80% без втрати візуальної якості.
2. **Впровадження атрибута `loading="lazy"` та `decoding="async"` для зображень нижче першого екрана:** браузер відкладає завантаження цих медіа до моменту наближення користувача до них під час скролінгу.
3. **Обов'язкове явне визначення розмірів `width` та `height` (або CSS `aspect-ratio`) на всіх тегах `<img>`:** це резервує простір у макеті ще до завантаження самого файлу і повністю ліквідує зсув сторінки (CLS).

### 6. Що означає абревіатура a11y та яка її головна мета у веб-розробці?
a11y — це нумеронім від англійського слова «Accessibility» (між першою літерою «A» та останньою «y» знаходиться рівно 11 символів). Її головна мета — проектування та створення веб-інтерфейсів, якими можуть безперешкодно користуватися всі категорії людей, незалежно від їхніх фізичних, сенсорних або когнітивних можливостей (користувачі скрінрідерів із вадами зору, люди з дальтонізмом, особи з порушеннями моторики, що використовують виключно клавіатуру, люди похилого віку або ті, хто перебуває у тимчасових обмежених умовах).

### 7. Чому використання семантичного HTML важливіше для Accessibility, ніж побудова інтерфейсу виключно на тегах `<div>` та `<span>`?
Теги `<div>` та `<span>` є семантично «нейтральними» (вони не несуть жодної інформації про призначення елемента). Семантичні ж теги (`<header>`, `<nav>`, `<main>`, `<article>`, `<section>`, `<footer>`, `<button>`, `<input>`) мають вбудовану браузерну семантику та автоматично створюють так зване «Accessibility Tree» (Дерево доступності). Завдяки цьому скрінрідери повідомляють користувачеві тип елемента («кнопка», «навігація», «основний зміст»), дозволяють переміщатися по орієнтирах (Landmarks) та забезпечують нативну доступність клавіатури без необхідності ручного додавання десятків ARIA-атрибутів.

### 8. Для чого використовуються ARIA-атрибути, наприклад aria-label та aria-expanded?
ARIA (Accessible Rich Internet Applications) — це специфікація W3C, що дозволяє передавати додатковий контекст та стан динамічних компонентів до допоміжних технологій (скрінрідерів):
- `aria-label="..."` — надає текстову мітку елементам, які візуально представлені лише іконкою (наприклад, кнопка меню-гамбургера або іконка хрестика закриття модального вікна), щоб скрінрідер міг чітко озвучити призначення елемента;
- `aria-expanded="true|false"` — інформує про стан розгортання інтерактивного блоку (наприклад, чи відкрите зараз мобільне меню, акордеон або випадаючий список).

### 9. Розкрийте різницю між процесами Continuous Integration (CI), Continuous Delivery та Continuous Deployment (CD).
- **Continuous Integration (CI — Неперервна інтеграція):** практика частого об'єднання коду всіх розробників у спільну гілку, де кожний коміт автоматично проходить збірку, синтаксичний лінтинг та автотести для виявлення дефектів на ранніх етапах.
- **Continuous Delivery (CD — Неперервна доставка):** розширення CI, за якого перевірений релізний білд автоматично готується до розгортання в стейджинг- або продакшн-середовище, але сам фінальний реліз активується людиною (ручне натискання кнопки «Deploy»).
- **Continuous Deployment (CD — Неперервне розгортання):** найвищий рівень зрілості автоматизації, за якого кожна зміна коду, що успішно пройшла всі етапи CI-пайплайну, автоматично та без жодного людського втручання публікується безпосередньо на продакшн-серверах у режимі реального часу.

### 10. Яку послідовність кроків проходить код в межах CI/CD пайплайну (конвеєра) після виконання команди git push origin main?
1. **Детектування події:** вебхук GitHub фіксує пуш у захищену гілку `main` та ініціює робочий процес GitHub Actions.
2. **Ініціалізація віртуальної машини (Runner):** запуск чистого контейнера Ubuntu Latest.
3. **Витягування вихідного коду (`actions/checkout@v4`):** клонування актуального зрізу репозиторію в робоче середовище.
4. **Налаштування інструментарію (Setup Node.js):** завантаження необхідної версії інтерпретатора середовища.
5. **Валідація та статичний аудит:** перевірка наявності критичних файлів, синтаксису HTML/CSS, цілісності JS-модулів.
6. **Автоматичний білд та розгортання:** передача оптимізованих файлів на хмарний сервер (GitHub Pages / Vercel).
7. **Звітність та зміна статусу:** присвоєння коміту статусу успіху (зелена галочка) та оновлення живого вебсайту.

### 11. Чому при розміщенні QR-коду на сайті обов'язково потрібно дублювати його текстовим посиланням, та який рівень корекції помилок (Error Correction) краще обирати?
- **Дублювання текстом є суворою вимогою доступності (WCAG / a11y):** незряча людина, що користується скрінрідером, або користувач на ПК фізично не можуть «відсканувати» графічне зображення QR-коду з власного монітора. Наявність поруч доступного клікабельного текстового посилання гарантує рівний доступ до контенту для всіх.
- **Рівень корекції помилок:** рекомендовано обирати рівень **H (High)**. Цей рівень відновлює до 30% пошкоджених даних, забезпечуючи стабільне сканування навіть за умов відблисків сонця, забруднення лінзи камери або накладання по центру QR-коду фірмового логотипа компанії.

### 12. Що таке QR Code Generator з технічної точки зору фронтенд-розробки та як працює алгоритм його зчитування смартфоном?
- **Технічна суть фронтенд-генератора:** це алгоритмічний модуль (бібліотека JavaScript або Python-пакет), що перетворює текстову строку (URL) у двійковий масив даних. За допомогою алгоритмів кодування Ріда-Соломона (*Reed-Solomon Error Correction*) генерується двовимірна матриця білих та чорних модулів, яка візуалізується у форматі SVG, HTML5 Canvas або растрового PNG.
- **Алгоритм зчитування смартфоном:** камера захоплює зображення, алгоритм комп'ютерного зору знаходить три кутові квадрати позиціонування (*Finder Patterns*), компенсує кут нахилу та перспективу, аналізує сітку модулів, застосовує алгоритм виправлення помилок для декодування байтів і транслює результат у клікабельний URL-лінк для браузера.
