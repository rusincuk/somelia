В ролі QA Engineer було проведено серію стрес-тестів з метою виявлення прихованих вразливостей згенерованого ШІ коду та реалізовано алгоритмічні гварди захисного програмування (Defensive Programming):

| № / Вхідні дані | Первинна поведінка (Баг) | Застосований захисний гвард (Defensive Fix) | Фінальний результат |
| :--- | :--- | :--- | :--- |
| 1. Порожнє поле ('') | NaN грн на екрані, ціна падає | rawValue.trim() === '' -> блокування підсумку | Помилка: 'Введіть кількість гостей (1-50)' |
| 2. Від'ємне (-5) | Сайт показував -2 950 грн ('борг') | guests < 0 -> перевірка від'ємності | Помилка: 'Кількість гостей не може бути від'ємною' |
| 3. Нуль (0) | Загальна сума = 0 грн | guests === 0 -> перевірка мінімуму | Помилка: 'Мінімальна кількість гостей — 1 особа' |
| 4. Астрономічне (999999) | Число вилазило за рамки UI | guests > MAX_GUESTS (50) -> обмеження | Помилка: 'Максимум 50 гостей для онлайн-розрахунку' |
| 5. Дробове (3.7) | 3.7 гостей, 1.85 пляшки | !Number.isInteger() -> Math.round(3.7) | Автоматично нормалізовано до 4 гостей |
| 6. Нечислові ('abc', '<script>') | NaN грн, ризик XSS | Number.isNaN() + textContent | Помилка валідації, XSS неможливий |
| 7. Швидке хаотичне введення | Мерехтіння та затримки | Миттєвий перерахунок через input | Стабільне оновлення без лагів |
| 8. Зміна формату дегустації | Потрібно було натискати кнопку | Слухач події change на select | Миттєвий автоматичний перерахунок суми |
| 9. Клік по чекбоксах | Перерахунок лише після інпуту | Слухачі change на чекбоксах | Миттєве додавання вартості послуг |
| 10. Відсутній DOM-елемент | TypeError: Cannot read properties of null | Рання перевірка if (!el) return | Fail-Safe: безпечний вихід без аварій |

# 7. Відповіді на 15 контрольних запитань

1. Що таке інтерактивний віджет в контексті веброзробки? Наведіть приклади.

Інтерактивний віджет — це самостійний динамічний компонент інтерфейсу вебсторінки, що володіє власною бізнес-логікою, вміє обробляти події користувача в реальному часі та перераховувати результат без повного перезавантаження сторінки. Приклади: калькулятор дегустаційного сету, конфігуратор піци чи напою, калькулятор вартості розробки сайту, погодний інформер, валютний конвертер.

2. Поясніть різницю між Happy Path та Edge Case.

Happy Path (ідеальний сценарій) — це послідовність дій, за якої користувач вводить абсолютно правильні, очікувані дані без помилок. Edge Case (граничний/винятковий випадок) — це аномальна або екстремальна ситуація на межі допустимих параметрів (від'ємні числа, нулі, порожні поля, дробові значення, астрономічні числа, вставка спецсимволів), яку система зобов'язана коректно обробити без аварійного збою.

3. Що таке Defensive Programming (захисне програмування)?

Захисне програмування — це методологія розробки ПЗ, за якої код пишеться з презумпцією того, що будь-які вхідні дані ззовні є потенційно некоректними, неповними або шкідливими. Його мета — запобігти падінню програми, використати безпечні резервні значення (Fail-Safe) та надати користувачу зрозуміле людське повідомлення про помилку.

4. Які основні Edge Cases ви тестували в своєму віджеті? Назвіть мінімум 4 випадки.

1) Порожнє поле введення; 2) Від'ємна кількість гостей (-5); 3) Введення нуля (0 гостей); 4) Введення дробових чисел (3.7 гостей); 5) Аномально великі числа (999999); 6) Введення нечислових символів ('abc').

5. Що означає поява NaN в результаті розрахунку? Чому це виникає?

NaN (Not-a-Number) — це спеціальне числове значення в JavaScript, яке сигналізує про помилку виконання математичної операції над нечисловими типами (наприклад, спроба помножити рядок 'abc' або undefined на число, чи парсинг порожнього рядка через parseFloat).

6. Як ви захищали код від порожнього поля та від’ємних значень?

За допомогою попередніх перевірочних гвардів (Guard Clauses):
• if (!rawValue || rawValue.trim() === '') -> показ повідомлення про помилку та блокування розрахунку.
• if (guests < 0) -> блокування підсумку та виведення: 'Кількість гостей не може бути від'ємною'.

7. Яку роль має подія input та change при створенні інтерактивного віджета?

• Подія input спрацьовує миттєво при кожній зміні вмісту текстового чи числового поля (навіть при кожному натисканні клавіші чи вставці), забезпечуючи справжній 'живий' відгук без кнопки.
• Подія change спрацьовує після завершення вибору або втрати фокусу, що є ідеальним для випадаючих списків (<select>) та чекбоксів (<input type='checkbox'>).

8. Як ви перевіряли роботу віджета? Які інструменти використовували?

Використовувалися інструменти розробника Chrome DevTools: вкладка Console (перевірка відсутності червоних помилок Runtime Errors, увімкнений режим Preserve log), вкладка Elements/Inspect для маніпуляції атрибутами DOM, режим Toggle Device Toolbar для тестування адаптивності на різних мобільних розширеннях (320px–1440px).

9. Що потрібно робити, якщо в консолі з’являється помилка TypeError: Cannot read properties of null?

Ця помилка виникає, коли скрипт намагається звернутися до властивості чи методу елемента, якого немає в DOM (getElementById повернув null). Для виправлення необхідно: 1) перевірити правильність написання id елемента в HTML; 2) переконатися, що скрипт запускається після DOMContentLoaded; 3) додати захисну перевірку (гвард): if (!element) return; перед викликом його методів.

10. Наведіть приклад хорошого промпту до ШІ для виправлення Edge Cases.

«Ти — Senior QA Engineer. У полі #guests-count віджета введено значення -5. Калькулятор відобразив -2950 грн. Завдання: проаналізуй причину логічного багу, додай захисний гвард для заборони від'ємних значень та виведи зрозуміле повідомлення під полем через Tailwind CSS. Не переписуй весь код, надай лише змінену функцію calculate().»

11. Чому важливо обмежувати максимальне значення в полях (наприклад, max='500')?

1) Захист інтерфейсу від переповнення (Integer Overflow) та виходу верстки за межі блоку; 2) Захист від втрати точності великих чисел у JS (Number.MAX_SAFE_INTEGER); 3) Дотримання реальних бізнес-обмежень (наприклад, онлайн-сервіс фізично не може обслужити банкет на 1 000 000 гостей без попереднього контракту).

12. Як ви інтегрували віджет в свій основний лендинг?

Віджет оформлено у вигляді окремої семантичної секції <section id='tasting-calculator'> на сторінці pairing-wizard.html, використано стилізацію Tailwind CSS з палітрою бренду SOMELIA, а JS-скрипт винесено в ізольований файл js/widget.js та підключено перед </body>.

Використано міжнародний стандарт Conventional Commits:

• git commit -m "docs: додати звіт лабораторної роботи №11 з розробки віджетів та Edge Cases"

14. Як відбувається автоматичний деплой після git push?

При виконанні команди git push origin main GitHub отримує новий комміт і надсилає Webhook-тригер на платформу хостингу (GitHub Pages / Vercel / Netlify). Хмарний сервіс автоматично клонує оновлену гілку main, проводить білд та розгортає нову версію сайту на Edge-серверах за 20–40 секунд без участі розробника.

15. Які головні висновки ви зробили з цієї лабораторної роботи щодо якості коду?

Справжня якість фронтенд-коду визначається не тим, як програма поводиться в ідеальних умовах (Happy Path), а її стійкістю до непередбачуваних та некоректних дій користувача (Edge Cases). Захисне програмування, сувора валідація, безпечне виведення (textContent) та ретельне QA-тестування через DevTools є обов'язковими стандартами професійної веброзробки.
